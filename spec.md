# Project Spec: expense-tracker — Phase 1 (LLM features)

## Goal

Add two LLM-powered endpoints to the existing expense-tracker FastAPI service:

1. **Natural-language expense input** — user POSTs free-form text ("lunch with Bob at Bombay Brasserie, 850"), service returns a structured expense ready to be created (or creates it directly via a convenience endpoint).
2. **Spending insights** — user GETs a narrative summary of their spending for a given month or category, generated by an LLM reading their actual data.

The build sits ON TOP of v0 — do not modify v0 endpoints, schemas, or tests beyond what's strictly necessary. The orchestrator must read CURRENT_STATE.md before planning.

## Scope

### In scope (Phase 1)
- New module `app/llm.py` — Groq client wrapper with model selection, retry on transient errors, graceful degradation on rate-limit failures
- New module `app/parser.py` — `parse_expense_text(text: str) -> ParsedExpense` using structured LLM output (JSON mode or tool-calling)
- New module `app/insights.py` — `generate_monthly_insight(month: str)`, `generate_category_insight(category: str)` reading from the DB and generating narrative summaries
- New endpoints in `app/main.py`:
  - `POST /expenses/parse` — body `{"text": "..."}` returns `ParsedExpense` (does NOT save)
  - `POST /expenses/from-text` — body `{"text": "..."}` parses + creates, returns the new `Expense`
  - `GET /insights/monthly?month=YYYY-MM` returns `{"month": "...", "narrative": "...", "stats": {...}}`
  - `GET /insights/category?category=...&since=YYYY-MM-DD` returns `{"category": "...", "narrative": "...", "stats": {...}}`
- New Pydantic schemas in `app/schemas.py`:
  - `ParsedExpense` (the LLM's structured output)
  - `TextInput` (request body for parse / from-text)
  - `Insight` (response shape for insights endpoints)
- Config via `.env` and pydantic-settings:
  - `GROQ_API_KEY` (user supplies — see "Setup" below)
  - `LLM_MODEL` (default: `llama-3.3-70b-versatile`)
  - `LLM_FALLBACK_MODEL` (default: `llama-3.1-8b-instant`)
- Tests with **mocked LLM** (no real API calls in CI / test suite):
  - `tests/test_parser.py` — at least 8 parse test cases (see "Parser test cases" below)
  - `tests/test_insights.py` — happy path + LLM error path
  - `tests/test_llm_endpoints.py` — endpoint integration tests with mocked LLM
- **Eval script** `scripts/eval_parser.py` — runs the parser against the 8+ test cases using the REAL LLM, reports per-case pass/fail with diff, used manually after spec changes to gauge parser quality (NOT run in CI)
- README updates: new section "LLM features" with setup steps, env vars, example curls, link to eval script

## Free-tier service: Groq
- **Why Groq:** the user already has a Groq API key and has used it for past projects. Free tier is generous (Llama models, ~30 req/min on 70B). Fast.
- **Setup the user must do BEFORE running this iteration:**
  - Sign up at https://console.groq.com (free)
  - Generate API key
  - Create `.env` file in project root with `GROQ_API_KEY=gsk_...`
  - Add `.env` to `.gitignore` (orchestrator should verify this in step 1)
- **Rate limit handling:** the LLM client must catch rate-limit errors (HTTP 429) and either (a) retry once after a short wait, or (b) fall back to the 8B-instant model if the 70B is rate-limited. After two failures, return a structured error to the caller.

## Data shapes

```python
# In app/schemas.py

class TextInput(BaseModel):
    text: str  # 1-500 chars

class ParsedExpense(BaseModel):
    amount: float
    category: str
    description: str
    occurred_at: date  # default: today if LLM can't infer
    confidence: float  # 0.0-1.0, LLM's self-reported confidence

class Insight(BaseModel):
    scope: str          # e.g. "month:2026-05" or "category:food"
    narrative: str      # 2-4 paragraphs of plain prose
    stats: dict[str, float]  # the raw numbers the narrative references
    generated_at: datetime
```

## Parser test cases (mocked LLM responses; for manual eval too)

Test cases the parser must handle correctly (at minimum):

| Input text | Expected category | Expected amount | Notes |
|---|---|---|---|
| `"lunch with Bob at Bombay Brasserie, 850"` | food | 850.0 | merchant in description |
| `"uber to office 240"` | transport | 240.0 | infer category |
| `"₹1500 for groceries yesterday"` | groceries | 1500.0 | parse rupee symbol, date offset |
| `"electricity bill 2340"` | utilities | 2340.0 | bill→utilities |
| `"netflix 649"` | entertainment | 649.0 | subscription |
| `"medicine 280"` | health | 280.0 | |
| `"5000 rent"` | rent | 5000.0 | reversed order |
| `"coffee 180"` | food | 180.0 | small purchases |

These cases drive both unit tests (with mocked LLM) AND the manual eval script (with real LLM). The mock responses match the table; the real eval validates whether the LLM actually gets these right.
